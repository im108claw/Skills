# とーや 外部送信ゲート（明示許可必須）

問い合わせフォーム・メール・DM・外部サイト投稿など、**外に届く操作**の共通ルール。
とーや訂正（2026-08-29）: **明示の送信許可がない限り送信しない**。

## When to Use

- Web 問い合わせ／応募／予約フォーム
- Gmail / メーラー送信・返信
- 外部チャット DM、店舗・採用への連絡
- 「書いて」「入れて」「下書きして」「バックグラウンドで動かして」系の依頼で、送信まで含むか判断するとき

X 予約投稿は別スキル（`x-browser-native-posting` / `x-short-post-ops`）だが、**送信・公開の明示許可**は同じ精神で扱う。

## ハードルール

1. **デフォルトは下書きまで**  
   調査・カレンダー確認・文面作成・フォーム入力準備・スクショ確認までは可。  
   **submit / send / 予約確定 / 公開** は不可。

2. **送信してよい明示語だけが許可**（その場の文で足りる）  
   例: 「送信して」「送って」「送信許可」「submit して」「この内容で出して」  
   次は **許可に数えない**: 「書いて」「入れて」「動かす」「お願い」「お任せ」「バックグラウンドで」「続けて」「完成させて」

3. **曖昧なら止めて確認**  
   文面と宛先（URL / To）を見せ、「この内容で送信してよいか」と聞く。勝手に解釈して送らない。

4. **一度の許可の範囲**  
   許可はその1通・1フォーム・明示された対象だけ。別宛先・別本文への流用は再許可。

5. **送信後は証拠を残す**  
   完了ページ文言 / message id / 予約一覧 read-back / スクショ。主張だけで終わらない。

## 標準手順（フォーム・外部連絡）

1. 対象 URL / 宛先を読む（項目名・必須・reCAPTCHA 有無）。
2. 本人情報は vault `profile.md` 等の確な出典から（本名は「姓 + 半角スペース + 名」など指定どおり）。
3. 日程が絡むなら `toya-schedule-coordination` + Calendar 全関連カレンダー。プレースホルダー禁止。
4. **下書き全文**をチャットに出す（名前・メール・件名・本文）。
5. **送信許可を待つ**。許可前に submit しない。
6. 許可後のみ送信 → 完了画面/応答を検証 → 証拠パスを報告。

## ピットフォール

1. 「内容を入れて」「バックグラウンドで動かして」＝送信許可だと思う（**誤り**）。
2. 日程スキルの「外部副作用は承認なしに行わない」を、フォーム submit だけ例外扱いする。
3. reCAPTCHA 突破できた勢いで、確認なしに確定する。
4. `+alias` メールと本チャンメールを取り違える（指定を再読する）。
5. 送信成功をログや「多分送れた」で済ませ、完了ページを読まない。
6. **Job カレンダー反映と送信を混同する**（2026-09-15）: 店都合シフトの Calendar 更新は送信ゲート外（即反映可）。逆に「下書きして」「カレンダー直して」＝メール送信許可ではない。
